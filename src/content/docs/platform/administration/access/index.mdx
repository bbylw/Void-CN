## 登录

浏览器管理后台的地址是 `<API URL>/admin`，打开后用安装时选定的管理员登录方式登入。在全新的安装上，按打印出来的管理员设置指引创建第一个管理员用户。你不需要先创建应用，也不需要先通过 CLI 登录。

先连接平台的 API 地址，再以管理员身份登录：

```sh title="登录平台"
void connect platform.example.com --no-login
void platform auth login
```

第一条命令保存连接，第二条会打开浏览器完成登录，并把管理员会话写入系统钥匙串。会话有效期一小时，并且按平台分别存储。

任何时候都可以查看当前登录的账户：

```sh
void platform auth status
```

它会显示你的账户、会话的过期时间，以及这个平台上可用的功能。要结束会话，运行 `void platform auth logout`。

如果平台受 Cloudflare Access 保护，`void connect <url>` 会在 Void 登录之前先处理公司身份登录。交互式的 Access 认证使用本地安装的 `cloudflared`，并把它短期有效的凭据按平台 origin 存入系统钥匙串。你不需要手动复制浏览器 cookie。

在 CI 中，把[项目部署令牌](/docs/platform/installation/first-deployment)与你的 Access 凭据一起放进按 origin 组织的 `VOID_ACCESS_CREDENTIALS`。Access 服务令牌不能授权一次 Void 部署。所需的 origin 与格式见 [CI 部署配置](/docs/platform/installation/first-deployment)。

## 选择平台

如果你管理多个平台，可以列出连接并指定默认平台：

```sh
void platform list
void platform use <connection-id>
```

也可以用 `--connection` 只为单条命令选择平台：

```sh
void platform user list --connection <connection-id>
```

使用连接列表里给出的 ID 或 URL。即使你在某个部署目标不同的应用目录里运行命令，管理类命令仍然使用这个选择。

## 恢复管理员登录

如果没有管理员再能使用已配置的身份提供方，安装方可以用具备 Cloudflare 管理权限的账户、直接的数据库访问权限，以及最初的加密恢复凭据来恢复一位已有的管理员：

```sh
void platform config auth recover company --installation <id> --file recovery.json
```

这个文件用于指明已存在的账户，例如 `{"administratorUserId":"existing-admin-id"}`。恢复流程会发起一次真实的登录测试，并在恢复访问权限之前要求你确认那个精确的身份。它不会创建新的管理员。若要改用替代的提供方，请在 `configuration` 中带上它的非机密配置和新的连接 ID，并通过 `--client-secret-env <name>` 提供密钥。若要轮换已有提供方的密钥，保留它的连接 ID 与身份配置。

如果使用 `--yes`，还要在文件里用精确的 `issuer` 与 `subject` 固定 `expectedIdentity`。一次成功的浏览器登录仍然是必需的。用 `--plan` 可以在开始恢复之前预览受影响的管理员与连接。

## 给用户开通访问权限

在管理后台打开 **Settings**，或运行 `void platform config auth`，来添加、测试、启用或禁用登录方式。Access 防护与登录方式是相互独立的设置。测试提供方时，它会先显示通过认证得到的账户，再由你显式关联或启用该配置。

安装之后要更换公司身份这道关卡，请使用当初安装时的那台机器及其保存的恢复凭据：

```sh
void platform config auth protection show
void platform config auth protection enable --installation <id>
void platform config auth protection disable --installation <id>
```

启用时可以选择新建应用或连接到已有应用。它会检查每一个 API、代理以及已配置的后台 origin，并要求公司用户登录。更改防护会结束所有当前的人类会话，之后需要重新登录。在移除用于公司注册的关卡之前，先另选一条已验证的公司规则或受限注册。移除防护后，Cloudflare 上的应用会保留下来，由你有意识地清理。禁用 Access 登录方式并不会移除这道关卡。

用户可以用 `void account link <connection-id>`，或在可选的后台里通过 **Account**，为已有账户添加另一个已启用的登录方式。如果提示要求，请先重新登录，然后用额外的提供方认证并确认所显示的身份。仅凭邮箱地址相同不会关联账户。

在管理后台打开 **People → Access** 来选择谁能加入、邀请成员、管理单个的注册许可。选择**公司批准或逐个批准的用户**后，符合你配置的公司规则的人会自动创建账户，同时仍允许显式的邀请与允许名单授权。在任何人才抵达登录页之前，平台边缘的公司防护依然生效。

当选定邀请/允许名单注册时，把同事的 GitHub 登录加入允许名单，就能让他用 GitHub 加入：

```sh
void platform signup allow github teammate
```

Void 会显示这次改动并请你确认。之后这位同事就可以用平台 URL 运行 `void connect` 并登录。

同样地，你可以放行一个邮箱地址或整个邮箱域名：

```sh
void platform signup allow email teammate@example.com
void platform signup allow email '*@example.com'
```

邮箱模式作用于平台的所有登录提供方。请给域名模式加上引号，好让 shell 把 `*` 原样传给 Void。

对于没有已验证邮箱的 OIDC 登录，改为按登录连接 ID 与提供方中稳定的 subject 来放行该身份：

```sh
void platform signup allow identity company-sso 'Employee-42'
```

连接 ID 取自 `void platform config auth list` 的显示，subject 用身份提供方报告的确切值。匹配区分大小写，不会推断邮箱地址，也不会关联到其他账户。该登录方式上已配置的域名或分组限制仍然适用，并且账户以普通用户身份加入。用 `void platform signup disallow identity company-sso 'Employee-42'` 撤销这条授权。

要通过邮箱邀请别人，使用：

```sh
void platform invitation send alex@example.org
```

邀请会为那个确切的邮箱地址开通注册权限。此人必须用一个能提供相同已验证邮箱的登录方式登录。如果平台已配置邮件投递，Void 还会发送连接说明。即使投递不可用或失败，这条授权依然有效：把平台的 `/invite` 页面或 `void connect '<平台 URL>'` 命令自己转给对方即可。管理后台会把投递结果与邀请的待处理、已接受、已撤销状态分开展示。

用下面的命令查看当前的访问设置与邀请：

```sh
void platform signup show
void platform invitation list
```

相关账户被删除后，邀请记录依然保留。当某个账户的登录方式已不存在时，记录中保存的操作者 ID 仍然可见。

`void platform signup open` 允许任何人注册。每个注册者都能在你的应用域名上部署应用，因此在放开注册之前，请先了解这些应用如何[共享 cookie](/docs/platform/installation/domains)。用 `void platform signup restrict` 可重新要求匹配允许名单。撤销一条允许项只影响之后的注册，不会停用已有的账户。

## 关联应用

把独立的应用注册为 OAuth 客户端，见[关联应用](/docs/platform/administration/connected-apps)。用户在 Void 上连接自己的身份，并逐个批准每次发布。
