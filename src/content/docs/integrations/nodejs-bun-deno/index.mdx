---
title: Node.js、Bun 与 Deno
description: 为 Node.js、Bun 或 Deno 构建 Void 服务端，并运行在你自己的机器、容器或其他宿主上。
---

在 `void.config.ts` 里设置 `target`，即可为 Node.js、Bun 或 Deno 构建。产出的服务端可以运行在你自己的机器、容器或托管服务商那里。

```json
{ "target": "node" }
```

## 上手

### 1. 配置 target

```json
// void.config.ts
{ "target": "node" }
```

### 2. 安装服务端依赖（仅 Node.js）

Node.js 需要额外安装 `@hono/node-server` 作为依赖。Bun 和 Deno 使用自带的 HTTP 服务器。

```bash
npm install @hono/node-server
```

### 3. 开发

```bash
npx vite dev
```

开发服务器会在你改动路由与页面时重新加载它们。

### 4. 构建并运行

```bash
npx vite build
node dist/ssr/index.js
```

Bun：

```bash
bunx vite build
bun dist/ssr/index.js
```

Deno：

```bash
deno run -A npm:vite build
deno run -A dist/ssr/index.js
```

这些命令都在应用目录下执行。服务器默认监听 `PORT`（环境变量），未设置时用 `3000`。

部署时要把 `dist/ssr` 和 `dist/client` 一起发布。

## 构建产物

构建会产出两个入口：

```text
dist/
  ssr/
    app.js       ← 带静态资源中间件的 Hono 应用（默认导出）
    index.js     ← 引入 app.js 并启动 HTTP 服务器
  client/        ← 静态资源（仅 pages 模式）
    .vite/manifest.json
    assets/
      ...
```

- **`app.js`：** 导出 Hono 应用实例。用于编程式嵌入、测试或自定义服务器方案。
- **`index.js`：** 引入 `app.js` 并启动服务器，生产环境运行的就是它。

`vite preview` 同样使用 `app.js` 在本地提供服务。

依赖 `void` 的安装包会被打进 `dist/ssr`。如果它们的某个依赖用到原生插件，或者会读取自己代码旁边的文件，请把那个依赖（按该包使用的版本）加进应用的 `dependencies`，构建就会把它交给 Node 处理。

## 可用的能力

以下 Void 特性在所有 target 上表现完全一致：

- [基于文件的路由](/docs/server-routing)（`routes/`、`middleware/`）
- 带 SSR 的 [Pages 模式](/docs/pages-routing)（React、Vue、Svelte、Solid）
- [带类型的 fetch 客户端](/docs/typed-fetch)（`void/client`）
- [自定义响应头](/docs/edge/headers)（`routing.headers`）
- [重定向](/docs/edge/redirects)（`routing.redirects`）
- [静态站点生成](/docs/ssg)
- 用 [Vite preview](https://vite.dev/guide/cli#vite-preview) 在本地验证生产构建

## 有差异的部分

### 环境变量

服务端变量请通过宿主环境提供，读取方式：Node.js 或 Bun 用 `process.env`，Deno 用 `Deno.env.get()`。`void/env` schema 与密钥工作流依赖 Cloudflare。

浏览器侧代码使用 Vite 的 `import.meta.env.VITE_*`，这些值在构建时被内联，绝不能包含密钥。

### 没有 Cloudflare 绑定

以下导入在非 Cloudflare target 上**不可用**，会产生编译期错误：

| 导入           | Cloudflare 特性         |
| -------------- | ----------------------- |
| `void/db`      | D1（SQL 数据库）        |
| `void/kv`      | KV（键值存储）          |
| `void/storage` | R2（对象存储）          |
| `void/auth`    | Void 托管的 Better Auth |
| `void/ai`      | Workers AI              |
| `void/sandbox` | Cloudflare Sandboxes    |
| `void/env`     | 带类型的环境变量 schema |

需要数据库或存储时，请使用外部服务商，并通过标准 Node.js 库连接。

WebSocket 路由文件（`*.ws.ts`）需要 Cloudflare。你仍然可以用 `void/ws` 的浏览器客户端去连接一个单独托管的 WebSocket 服务。

### 没有定时任务运行时

你依然可以在 `crons/` 里定义 [cron 任务](/docs/jobs)，它们会被编译进产物，但没有内置调度器去调用。在 Cloudflare 上，Workers Cron Triggers 会自动调用 `scheduled` 处理器；在 Node.js 上，你需要外部调度器（例如 `node-cron`、systemd timer 或托管平台的 cron）来触发导出的处理器。

### 没有邮件收件

[收件邮件处理器](/docs/email/receiving)与 `sendEmail` 需要 Cloudflare。其他 target 上请使用外部邮件服务商。

### 没有预渲染

[边缘预渲染](/docs/edge/prerendering)需要 Cloudflare。构建期的[静态生成](/docs/ssg)在所有 target 上都可用。

### 没有 `void deploy`

`void deploy` 面向 Cloudflare 与 Void 平台的部署。Node.js、Bun 或 Deno 请运行 `vite build`，然后按托管服务商的流程部署 `dist/`。

### 会被忽略的配置字段

在非 Cloudflare target 上，Void 会给出警告并忽略这些 Cloudflare 专用的 `void.config.ts` 字段：

- `inference.bindings`：Cloudflare 绑定配置
- `remote`：远端绑定代理
- `worker`：Cloudflare 专用配置
- `routing.revalidate`：边缘缓存，仅 Cloudflare 支持

如果通过 `void/auth`、`void/client` 或 `auth.ts` 启用了认证，Void 会让非 Cloudflare target 的构建失败。Node/Bun/Deno 部署请直接使用 Better Auth。

## 编程式使用

由于 `app.js` 导出了 Hono 应用，你可以把它引入自定义服务器：

```ts
import app from './dist/ssr/app.js';

// 与任意 Node.js HTTP 框架配合使用
const response = await app.fetch(new Request('http://localhost/api/hello'));
console.log(await response.json()); // { message: "Hello from Node.js!" }
```

这对测试、嵌入 Express/Fastify，或者运行接受 `fetch` 处理器的 serverless 环境都很有用。

### 从别处提供 client 构建产物

要把应用打包成[单一可执行文件](https://nodejs.org/api/single-executable-applications.html)，给 `app.fetch()` 传入一个带 `fetch(request)` 方法的 `ASSETS` 对象。Void 会用它来获取 client manifest、脚本、样式与 public 文件，而不再读取 `dist/client`。

Node.js 下，按 URL 路径保存这些资源，包括 `/.vite/manifest.json`、`/assets/…` 以及从 `public/` 拷来的文件：

```ts
import { getAsset } from 'node:sea';
import { serve } from '@hono/node-server';
import app from './dist/ssr/app.js';

const types: Record<string, string> = {
  '.js': 'text/javascript',
  '.css': 'text/css',
  '.json': 'application/json',
};

const ASSETS = {
  async fetch(request: Request): Promise<Response> {
    const { pathname } = new URL(request.url);
    try {
      const type = types[pathname.slice(pathname.lastIndexOf('.'))] ?? 'application/octet-stream';
      return new Response(getAsset(pathname), { headers: { 'content-type': type } });
    } catch {
      return new Response('Not Found', { status: 404 });
    }
  },
};

serve({ fetch: (request, env) => app.fetch(request, { ...env, ASSETS }), port: 3000 });
```

添加 `ASSETS` 时要保留服务器原有的 `env` 值，这样 `getConnInfo()` 才能读到当前请求。

Bun 下，用 `{ type: 'file' }` 导入每个 client 文件，让 `bun build --compile` 把它们作为资源嵌入。这个模块要在每次 `vite build` 之后重新生成，因为文件名会随构建变化。不要把 client 脚本列为构建入口，否则 Bun 会把它们当成可执行代码打包：

```ts
// client-files.ts，在每次 `vite build` 之后生成
import manifest from './dist/client/.vite/manifest.json' with { type: 'file' };
import pagesClient from './dist/client/assets/pages-client-BZk7n9j7.js' with { type: 'file' };

const files: Record<string, string> = {
  '/.vite/manifest.json': manifest,
  '/assets/pages-client-BZk7n9j7.js': pagesClient,
};
export default files;
```

然后在编译出的可执行文件里提供这些资源，并把 Bun 的 `Server` 作为 `server` 传入，这样 `getConnInfo()` 仍然可用：

```ts
import files from './client-files.ts';
// server.ts，用 `bun build --compile server.ts --outfile server` 编译
import app from './dist/ssr/app.js';

const ASSETS = {
  async fetch(request: Request): Promise<Response> {
    const path = files[new URL(request.url).pathname];
    return path ? new Response(Bun.file(path)) : new Response('Not Found', { status: 404 });
  },
};

Bun.serve({ fetch: (request, server) => app.fetch(request, { server, ASSETS }), port: 3000 });
```
