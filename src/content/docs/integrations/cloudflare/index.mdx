Void 运行在 Cloudflare Workers 上。它会检测你的应用使用了哪些资源、创建对应绑定，并部署到你的账户。

## 绑定

在 Void 的路由与中间件里使用 `c.env`：

```ts
// routes/api/users.ts
import { defineHandler } from 'void';

export const GET = defineHandler(async (c) => {
  const { results } = await c.env.DB.prepare('SELECT * FROM users').all();
  return c.json({ users: results });
});
```

TanStack Start 与 React Router 可以直接从 `cloudflare:workers` 导入绑定：

```ts
import { env } from 'cloudflare:workers';

const { results } = await env.DB.prepare('SELECT * FROM users').all();
```

其他框架使用各自的绑定访问方式，请参照对应[框架的接入指南](/docs/frameworks)。

### TypeScript 配置

把 `void/env` 加入 TypeScript 的 types：

```json
{
  "compilerOptions": {
    "types": ["void/env"]
  }
}
```

它会提供绑定类型与 Workers 运行时类型。如果在 `void.config.ts` 里定义了自定义绑定，运行 `void prepare`，或者启动开发服务器、执行构建，就能在 `c.env` 上得到它们的类型。service 绑定与 Durable Object 绑定的 RPC 方法参见[自定义绑定类型](/docs/type-safety)。

### 可用的绑定

| 绑定         | 资源            | 在应用中的用法                    |
| ------------ | --------------- | --------------------------------- |
| `DB`         | D1              | `c.env.DB` 或 `void/db`           |
| `KV`         | KV              | `c.env.KV` 或 `void/kv`           |
| `STORAGE`    | R2              | `c.env.STORAGE` 或 `void/storage` |
| `AI`         | Workers AI      | `c.env.AI` 或 `void/ai`           |
| `ASSETS`     | 静态资源        | `c.env.ASSETS.fetch(request)`     |
| `QUEUE_*`    | Queues          | `defineQueue()` 或 `void/queues`  |
| 由文件名推导 | Durable Objects | `durable-objects/` 下的一个模块   |

需要启用、禁用或重命名某个推断出来的绑定时，使用[绑定配置](/docs/reference/resource-inference)。

## Cloudflare 配置

在 `void.config.ts` 中声明 Worker 设置：

```ts
import { defineConfig } from 'void/config';

export default defineConfig({
  worker: {
    compatibility_date: '2026-02-24',
    compatibility_flags: ['nodejs_compat'],
  },
  cloudflare: {
    name: 'my-app',
    services: [{ binding: 'API', service: 'my-api-worker' }],
  },
});
```

绑定数组、资源 ID、路由与 service 绑定都写在 `cloudflare` 下。Void 会保留你配置好的绑定，并补上缺失的推断资源。兼容性设置与变量以 `worker` 字段为准，参见[配置](/docs/config)。

当 Void 记录了资源 ID 或 Durable Object 迁移，请提交 `void.lock.json`。生成的 Cloudflare 配置不要放进 Git。需要适配器配置路径的框架使用 `.void-wrangler.jsonc`，各框架的接入指南会列出必需的选项。

环境变量在 `env.ts` 中声明，本地值写在 `.env` 里，生产环境的服务端值用 `void secret put` 设置，参见[环境变量](/docs/env-vars)。

## 部署到你自己的 Cloudflare 账户

在 `void init` 时选择 Cloudflare，然后部署：

```sh
void deploy
```

Void 会打开浏览器让你登录，如果你有多个账户，它会询问使用哪一个。浏览器没有自动打开时，跟着终端里给出的链接操作并确认打印出的代码。

如果之后再配置部署，运行 `void connect --platform cloudflare`。只想在某一次部署中选择 Cloudflare，运行：

```sh
void deploy --platform cloudflare
```

用 `void cloudflare login`、`void cloudflare status` 与 `void cloudflare logout` 管理登录状态。

### 部署已有的 Worker

对于已经直接部署到 Cloudflare 的现有 Void 应用，保留它根目录的 `wrangler.jsonc` 或 `wrangler.json`，然后运行：

```sh
void deploy
```

没有指定目标时，Void 会提出关联这个已有的 Worker。同意后登录并部署。Void 会把配置迁移到 `void.config.ts` 与 `void.lock.json`，保留绑定、变量、密钥、路由与定时任务。这两个文件都要提交。

首次部署只专注于把现有应用接上，关联完成后再添加资源、认证、迁移或其他运行时能力。如果该 Worker 存在更新的、未启用的上传版本，先在 Cloudflare 中启用或移除它，再重试。

就绪检查要么依赖已有的[版本元数据绑定](https://developers.cloudflare.com/workers/runtime-apis/bindings/version-metadata/)，要么依赖可访问的 [Version URL](https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/)。两者都没有时，Void 会在切流量之前停下。

预渲染页面可能需要一份新的 ISR 缓存。Void 会询问是否启用，并把选择保存为 `routing.isr`。选择 `false` 则这些页面每次请求都重新渲染。在 CI 中，请在部署前就设好这个选项。已有缓存会保留自己的 ID。

如果关联时报告缺少某个绑定，请把现有 Worker 的绑定名与资源 ID 填到 `cloudflare` 和 `inference.bindings` 中。重试时保留 `.void/cloudflare-link.json`。

之后如果要修改由控制台管理的触发器或可见性，先把当前的 `routes`、`workers_dev` 与 `preview_urls` 写进配置。关联之前把 `wrangler.toml` 转成 JSON/JSONC。命名环境需要各自独立的 Void 项目配置。

### 部署过程中发生了什么

Void 会创建缺失的资源、构建应用、检查密钥与迁移、上传 Worker、验证就绪状态，最后更新流量与触发器。资源 ID 保存在 `void.lock.json` 中。

构建或校验失败时，账户里可能已经开出了一些资源。第一次部署请只在一台机器上执行，提交 lock 文件之后再从其他机器或 CI 部署。

使用邮件的应用需要在 `void.config.ts` 里设置 `email.from`。Void 会在构建前检查域名配置，并在需要改动时先征询你。参见[邮件](/docs/email/domains)。

### 从 CI 部署

按需设置以下 CI 密钥与变量：

| 名称                                             | 什么时候需要                                                                                                                                  |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `CLOUDFLARE_API_TOKEN`                           | 必需。需要 Workers Scripts 的 Edit 权限、对所绑资源的读取权限，以及对 Void 负责开通的产品（provision）的编辑权限。                            |
| `CLOUDFLARE_ACCOUNT_ID`                          | 当这个 token 能访问多个账户时。                                                                                                               |
| `DATABASE_URL`                                   | PostgreSQL 与 MySQL 的资源开通与迁移。                                                                                                        |
| `CLOUDFLARE_WORKERS_SUBDOMAIN`                   | 启用了 workers.dev 且该版本没有预览 URL 时。填 `my-team` 或 `my-team.workers.dev`。当 `workers_dev` 为 false 时，账户子域名不会生成就绪 URL。 |
| `CF_ACCESS_CLIENT_ID`、`CF_ACCESS_CLIENT_SECRET` | 就绪 URL 受 Cloudflare Access 保护时。                                                                                                        |
| `CF_ACCESS_READINESS_ORIGIN`                     | Access 保护的是某个路由或自定义域名且 `workers_dev` 为 `false` 时，参见 [Cloudflare Access](#cloudflare-access)。                             |

邮件相关：先在本地运行 `void email setup --platform cloudflare`，提交 `void.lock.json`，并在 CI 中传入 `--require-email`。这个 token 还需要 Zone Read 与 Email Sending Edit；带有 `email/` 处理器的应用另需 Email Routing Edit。

#### Cloudflare Access

本地部署到受 Access 保护的 Worker 时，可以使用短时效的用户会话：

```sh
export CF_ACCESS_TOKEN="$(cloudflared access token --app=https://<worker>.<account>.workers.dev)"
```

Void 用 Access 凭据做就绪检查，但不会保存它们。如果检查被拒绝，部署就会失败。此时首次部署的引导流程可能已经在 Access 之后处于生效状态。

默认情况下，Void 只把 Access 凭据发往 `workers.dev` 的 URL。当 `workers_dev` 为 `false` 时，Void 可以通过你的第一个路由或自定义域名做就绪检查。要把凭据发往那里，就把该主机名的 origin 设为 `CF_ACCESS_READINESS_ORIGIN`：

```sh
export CF_ACCESS_READINESS_ORIGIN="https://app.example.com"
```

这个变量要设置在执行 `void deploy` 的 shell 或 CI 环境里。请填写你控制的、确实为这个 Worker 提供服务的主机名对应的精确 HTTPS origin；Void 会把 Access 凭据发到那里。

### 数据库与密钥

PostgreSQL 与 MySQL 需要在部署过程中提供 `DATABASE_URL`。Void 用它来配置 Hyperdrive 和跑迁移，但不会把它写进配置。MySQL 的 schema 变更可能在报错前已经部分生效，参见[失败的 MySQL 迁移](/docs/database/mysql)。

创建 Hyperdrive 需要具有 Hyperdrive 编辑权限的 API token。也可以先在 Cloudflare 中创建，再把它 ID 填到 `cloudflare.hyperdrive`；已有绑定用浏览器登录方式即可工作。

部署 schema 变更前先运行 `void db generate` 并提交迁移文件，这包括 Better Auth 的表。自定义的 D1 迁移目录、表与匹配模式都支持；要应用的迁移文件与已校验的历史不一致时，部署会停止。

用 `void secret put <NAME>` 设置生产环境的服务端值。Void 会保留远端已有的密钥，并在需要认证的应用里创建 `BETTER_AUTH_SECRET`。本地 `.env` 的值永远不会被部署上去。

### 就绪检查与回滚

Void 会先检查上传的版本，再给它导流量。如果 Worker 没有公开 URL——workers.dev 已关闭，且没有配置路由或自定义域名——Void 会跳过就绪检查直接激活。

就绪检查或触发器更新失败时，Void 会恢复上一次的部署。如果触发器更新失败且无法恢复原来的触发器（例如其他工具随后做过部署，或来自一个空的草稿），新版本会继续在服务流量，错误信息里会写明当前服务流量的版本号。

用 Void 部署之前，先在 Cloudflare 里完成或取消灰度发布（gradual rollouts）。

对于 Cloudflare 无法 staged 的已有 Durable Object Worker，请先审阅改动，再使用：

```sh
void deploy --platform cloudflare --atomic
```

想让每次部署都这样，设置 `deploy: { cloudflare: { mode: 'atomic' } }`。原子部署会在就绪检查之前就把流量切到新版本。Durable Object 的类迁移一旦越过其迁移边界就无法回滚。

新 Worker 可能需要先有一次生效的部署，之后才能做就绪检查。如果 staged 上传失败，请保留 `.void/cloudflare-candidate.json`，以便在同一份代码检出上重试。

查看或恢复版本：

```sh
void project status
void project rollback [version]
```

Void 在恢复代码的同时恢复记录过的触发器。没有完整触发器快照的版本会保留当前的路由与定时任务。数据库恢复是另一回事：撤销 D1 迁移请使用 [`void db restore`](/docs/reference/cli/database)。

#### 支持范围与限制

Void 可以部署原生应用、静态站点、SPA、受支持的 SSG，以及来自 TanStack Start、React Router、SvelteKit、Nuxt、Analog 与 Astro 的 Cloudflare 构建产物。vinext 适配器仍是实验性的。

- 原生应用支持 Void 的路由规则。直连 Cloudflare 目标上的框架应用，重定向、重写、兜底与响应头都要通过各自的框架或 Worker 来配置。
- `--skip-build` 适用于已有的静态产物。Worker 应用必须重新构建。
- 不支持 Cloudflare 的命名环境。每个目标请使用独立的 Void 项目配置。
- Sandbox 需要 Workers Paid 套餐与 Docker，套餐与 token 权限要求参见 [Sandbox 要求](/docs/sandboxes)。
- 向任意收件人发信，以及没有 `email/` 处理器的应用的全部发信行为，都需要 Workers Paid 套餐。有处理器的应用在 Workers Free 上仍可使用收件与已验证收件人，参见[邮件](/docs/email/domains)。
- Node.js、Bun 与 Deno 走[各自的部署路径](/docs/integrations/nodejs-bun-deno)。

Durable Object 的迁移历史提交在 `void.lock.json` 中。不要删除或重排已经部署的步骤。

### 管理已部署的应用

`void secret`、`void domain`、`void project status|list|logs|rollback` 以及远端 `void db` 命令都使用所选的账户与 Worker。日志是实时尾随输出。

自定义域名命令会立即更新路由。如果首次部署在 DNS 或 TLS 传播期间超时，请先在 Cloudflare 中确认域名状态，等 `/__void/ready` 可访问之后再重试。

`void project delete` 不会移除 Cloudflare 上的资源。请自行确认归属并在 Cloudflare 中删除它们。

### 本地开发

本地的 D1、KV 与 R2 绑定使用本地数据。生产环境的资源 ID 只在部署时使用。

连接 Cloudflare 之后，Workers AI 会在远端运行，因此开发期间的调用同样消耗你账户的额度。开发与预览中的远端绑定使用你 `void cloudflare login` 的会话；设置了 `CLOUDFLARE_API_TOKEN` 时使用它。

### 自己账户上的 AI

`ai.run()`、`ai.stream()` 与 `ai.image()` 使用你的 Workers AI 绑定。要用 provider 模型，请配置你的 AI Gateway，并把 provider 的密钥存成 Worker 密钥：

```ts
import { defineConfig } from 'void/config';

export default defineConfig({
  ai: { gateway: 'my-gateway' },
});
```

```sh
void secret put OPENAI_API_KEY
```

之后 `ai.provider('openai').fetch(...)` 就会使用这个 gateway 与密钥。示例参见 [AI 指南](/docs/ai)，账户用量可以用 [AI Gateway 分析](https://developers.cloudflare.com/ai-gateway/) 查看。

### 自己账户上的 ISR

[再验证](/docs/edge/revalidation)可以按全局、按路径或按页面配置，Void 会自动开通所需缓存。

`revalidate()` 会清除共享存储和当前数据中心的边缘缓存。其他数据中心在自身缓存寿命到期前仍可能返回缓存响应；在尚未渲染过该 HTML 的数据中心里，页面的数据请求会实时生成。

每次部署都从一份全新的缓存开始。
